# MeiliSearch vs Zinc 双引擎评测报告

> 2026-10-07 · 用户令"评测"。数据=同仓 6 件商品、14 查询×7 维度、性能 3 查询×20 轮中位。
> 复现：`node scripts/benchmark-engines.mjs`（评测脚本即本报告数字的唯一来源，单机单日工况）。
> 环境：MeiliSearch v1.54.3 / Zinc v1.0.0-beta3，同机 Windows，均空载暖态。

## 总分（搜索质量加权：精确 30%/容错 20%/联想 20%/泛词 15%/跨语 15%）

| 引擎 | 精确 | 错字 | 描述联想 | 泛词 | 拼音 | 英文 | 加权 |
|---|---|---|---|---|---|---|---|
| MeiliSearch | **0.97** | 0 | **1.00** | 0.92 | 0 | 0 | **0.63** |
| Zinc | 0.75 | **0.79** | 0.78 | 0.92 | 0 | 0 | **0.68** |

## 关键发现（数字之外的三件事）

1. **Zinc 的"容错"高分是宽泛的副产品，不是真容错**：搜"手代"（错字）Zinc 召回 100% 但精确率仅 25%——它把中文切成单字做 OR 匹配，任何含"手"的都回来。用户看到的是 4 件里 3 件不相关。Meili 则相反：不确定就不给（精确率高、召回为零）。
2. **Meili v1.54.3 对中文无官方错字容错**（本次实测与 v1.7.4 时期行为不同——v1.7.4 的"手代"命中更可能是分词巧合）。官方 typo tolerance 不覆盖 CJK，属能力边界非缺陷；中文容错两引擎都需外挂（如 pinyin-pro）。
3. **拼音与英文两引擎双双零分**——中文商品名场景下"shoudai"/"Boston"都搜不到，该需求只有外挂方案能解。

## 工程面（定性）

- MeiliSearch：商业公司支撑，两年 47 版稳定发版；自有 REST API 简洁；官方前端集成库；新版带向量混合检索与 MCP 端点。
- Zinc：ES 查询语法兼容（会 ES 的团队零成本）；项目经历改名/转型动荡（zinc→ZincObserve→zincsearch），现处 beta 阶段；聚合分析能力（ES 那套）。

## 结论

- **面向终端用户的搜索框（本店场景）：MeiliSearch 更好**——精确与联想是主路径（0.97/1.00），搜索框场景"给用户最想要的"优于"把可能的都给"。
- **宁可多给不能漏的场景（管理后台检索/审计式查询）：Zinc 的宽泛风格更合适**。
- **备胎定位：Zinc 合格**——快一倍、轻一半、DSL 兼容，故障切换已实战验证。
- 当前部署（Meili 主+Zinc 备+SQL 兜底）与评测结论一致，无需调整。
- 若要中文容错/拼音，两引擎都需要外挂 pinyin-pro——引擎选择不构成该决策的变量。

## 附：多语言实验（2026-10-07 同日补，临时索引已清理）

6 条多语言文档×9 查询，结果按语言排：

| 语言 | MeiliSearch | Zinc | 说明 |
|---|---|---|---|
| 英文精确 | ✓ | ✓ | 平 |
| **英文错字（Lether→Leather）** | **✓** | ✗ | Meili 拉丁容错独家 |
| **法文重音折叠（Cafe→Café）** | **✓** | ✗ | Meili 独家 |
| 日文（バッグ） | ✓ | **✗** | Zinc 无空格 CJK 切词垮 |
| 韩文（가방） | ✓ | ✓ | 韩文有空格，平 |
| 中文 | 精确/联想强，无容错 | 宽泛召回高，噪音同来 | 各有千秋（见正文） |
| 数字/SKU/连字符 | ✓ | ✓ | 平 |
| 单复数词形（bags↔Bag） | ✗ | ✗ | 都无词干提取 |
| 拼音 | ✗ | ✗ | 都需外挂 |

**语言能力合计：Meili 7/9 vs Zinc 6/9，且 Meili 的两项独家（拉丁容错+重音折叠）恰是英文搜索的核心体验**。Zinc 的短板集中在无空格分隔的语言（日文全垮、中文靠宽泛硬撑）。中文场景结论不变：Meili 主路径强、Zinc 宽泛备胎。
