## 3. 4 个第一性问题（v5 写作前的 hard stop）

### 问题 1：R3 不变式本身有必要吗？

**当前不变式**（`scripts/reconcile-orders.mjs:128-147` LIKE 模糊查）：
> "每个订单事件必须能在 audit_logs 表找到对应 module=orders 的行"

**问题**：
- 这个不变式隐含的假设 = "orders 业务事件必须入 audit_logs"
- 但 audit_logs 表的设计是"全工程审计事件流"（用户/订单/支付/产品/系统/安全）
- "订单业务事件必须入 audit_logs"——是"orders 模块"必须与其他模块同等待遇
- **但 v4.1 实施时没接 audit 写入**——这不是 audit_logs 缺，是**v4.1 工程实施遗漏**

**核心问题**：
- 选项 A：补 audit_logs 写入路径（v3/v4 方向）——这是"补外键"
- 选项 B：snapshot 表已有 operatorType/operatorId/correlationId/prevHash/recordHash 链——**snapshot 链本身就是审计证据**，audit_logs 表是"另一种审计"，两者不必然 1:1
- 选项 C：明确"两种审计各管一面"——snapshot 管"业务态变更证据"，audit_logs 管"请求维度审计"——**没有不变式**——不需要 R3 跨表对账

**需要业务侧回答**：R3 不变式**本意**是"快照必须有 audit_logs 行"，还是"snapshot 链本身是合规证据，audit_logs 是另一套证据"？

### 问题 2：9 条历史孤儿是 bug 还是设计债？

**事实**：
- 9 条 snapshot 在 dev 库 orders 表中**根本不存在**（orderId 1001/1002/1003 是孤儿）
- 9 条 snapshot 全在同一秒——**测试 fixture**
- audit_logs 0 行 orders 模块——**dev 库从未跑过真实订单业务事件**

**问题**：
- 这是 v4.1 schema 实施时**测试数据没回滚**（测试 fixture 留在库内）
- 不是"上线后漏审计"
- 真实生产环境如果跑过 orders 业务事件——应该已经有 audit_logs 行

**核心问题**：
- 选项 A：清掉这 9 条 fixture（dev 库 R3 = 0，债-10 治本）
- 选项 B：保留 fixture 视作"未来生产 R3 = 9 是真实缺口"——但生产 0 行 orders 模块意味着 R3 一定 = N

**需要业务侧回答**：dev 库 fixture 是清还是留？清后 dev 库 R3 立刻 = 0。

## 4. 选项 A/B/C 方案对比

### 选项 A：v4 方向继续（补 audit_logs 外键）

- 加 2 列 + R3 改真 JOIN
- 治本率宣称 100%
- **实测有 P0 致命**：log() 接受参数但不写库（I 席抓出）；R3 JOIN 两侧 correlationId 字面不等（IV 席抓出）
- 实施 3-4 人天，但 prod 10M+ 表承重数字全裸奔（II 席抓出）
- 反复打回 2 轮，**v5 需大量修订**

### 选项 B：明确"双轨审计"哲学（snapshot 链 = 业务态审计，audit_logs = 请求维度审计）

- 改 R3 不变式：从"快照必须有 audit_logs 行"→ "snapshot 链是订单业务态的合规证据"
- snapshot 已有 operatorType/operatorId/correlationId/prevHash/recordHash 链——**已经是 hash 链审计**
- audit_logs 加 orderId/correlationId 仍需（**跨表回查需要 FK**）——但**不是 R3 不变式的依据**
- 实施：只加 FK + admin 回查端点（不改 R3）
- 治本率 = "业务态有完整审计链"

### 选项 C：清 fixture + 不变式重定义

- 清 dev 库 9 条 snapshot fixture（是测试残留）
- R3 立刻 = 0
- **不补外键，不改 R3**
- 治本率 = "测试 fixture 已清，业务态有 hash 链"
