- 理由：这是稿内三个自家承诺（保链、禁重锚、erasure 分层）的互斥三角，不解决则核心构件（表）出不了图，且卡死的不只是 P4——是 P1 的 DDL。

## P1（5 项）

**F2｜domain_events 无 DDL/字段清单/索引/双方言迁移/新 canonical 键序**
- 位置：§3 裁决 1（"新表新纪元"）、§2 表第 4 行（仅给三元组+schemaVersion 四个字段名）；对照本仓迁移先例 `backend\src\database\migrations\20261005000001-add-audit-chain-columns.ts`（MySQL/TiDB 方言探测）与 `20261011000001-create-order-snapshots-table.ts`（sqlite/MySQL 双分支+CLUSTERED）。
- 实操影响：方案的**唯一新建物理构件**没有物理形态。缺：完整字段清单（链列 nullable 形态、中继状态标记、payload 列型）、索引（seq 唯一索引？轮询扫未链化行的谓词用什么索引？(aggregateType,aggregateId) 查询索引？）、双方言迁移（dev=better-sqlite3、生产=MySQL/TiDB，仓内先例均双分支）、以及**新表的 canonical 键序清单**——稿引 C5 教训立了"schemaVersion 开局内置"，却恰恰没给开局必须定死的键序本身；新纪元第一锤就砸在自己引的教训上。
- 理由：P1 行"表+中继+外锚"三件里"表"这件没有任何可评审物，无 DDL 则白名单投影（见 F5）、中继读谓词（F3）、对账 JOIN（P3 R3'）全部悬空。

**F3｜中继运行参数零数字、与全局 FIFO 互斥的吞吐相容性零讨论**
- 位置：§3 架构图（"中继（进程内定时/事件驱动）：读未链化 outbox 行→同中继事务补链列"）、§4 P1（"中继（轮询）"4 字）；对照 `backend\src\common\db-write-mutex.ts:28-35`（进程级 FIFO 全写队列）、B 员报告第 22 行（polling publisher 代价="轮询延迟/表扫描"）与第 155 行（TiDB 无 SKIP LOCKED）。
- 实操影响："中继（轮询）"**开不了工**：轮询间隔、每批行数上限、补链是单事务批量还是逐行事务（逐行=每行一笔事务+一次入队，批量=一笔事务顶住整个业务写队列若干毫秒到秒级）、重试几次进死信、死信表形态、告警走哪个通道——一个数字没有。且中继事务在 sqlite 单连接下必须同样过 `runExclusiveWrite`（C1 约束），与业务写**同队 FIFO 竞争**：FIFO 保证不饿死（`db-write-mutex.ts:24-25`），但两个方向的延迟耦合（大积压批阻塞业务、业务高峰推迟中继）稿完全未着墨，而 §7 自认生产量级待证——量级未知恰是必须给参数区间的理由，不是免给的理由。
- 理由：中继是与表并列的两大新构件之一，缺参数+缺吞吐分析=该构件处于"有名字无内容"状态。

**F4｜旧表冻结封存实操件缺失：写点清单、停写机制、终锚落点、过渡语义四无**
- 位置：§3 裁决 1（"停写、锚定当前头、归档声明"）、§4 P1/P2；对照实测写点（C 员卡+本次复核）：`products.controller.ts:174`（auditProductWrite，3 处调用）、`orders.service.ts:218`（M5 循环）、`audit.controller.ts:387-420`（**POST /audit/test 现役写入口**，管理员可调）。
- 实操影响：①"谁停"无清单——上述 5 个调用点稿一个没列，/audit/test 不摘则"冻结"随时被一次管理员点击打破；②"怎么停"无机制——删调用、加开关、还是 DB 层拦截（sqlite 触发器），语义与回滚面完全不同；③"锚定声明落哪"无落点——现锚文件 `docs\audit-chain-head.txt` 为追加式纯文本、"由人工执行"（头注明文），终锚行+封存声明写进该文件还是新卷宗、谁签发、`scripts/verify-audit-chain.mjs` 对封存后链的验证语义是否变化，均未讨论；④P1"只接管新写"与 P2"冻结"之间的过渡语义未说明——若 P1 接管后旧写路径并行活到 P2，双写病灶（本方案宣称根治的对象）在过渡期延续且互斥队列负载翻倍；若 P1 即切换，P2 的"冻结"只剩仪式，两句都写不清实施者就会各自解释。
- 理由：冻结封存是方案三大动作之一，其可执行件（写点清单/停写 PR 范围/终锚 procedure）为零。

**F5｜PII 防护时序倒置 + "接线既有 sanitizer"与"白名单投影"方向相反 + 事实表述不准**
- 位置：§3 裁决 5、§4 P2（"LogSanitizer 接线 + 白名单投影"排在 P1 验收之后）；对照 `backend\src\common\security\log-sanitizer.service.ts:47-60`（**黑名单掩码**：SENSITIVE_FIELDS+正则）、D 员 Q3（Art 25(1) 要求"design 时落实"最小化）。
- 实操影响：①P1 起订单/商品/退款事件开始落库，白名单投影 P2 才接——按 D 员 Q3 硬边界（buyerLogonId/sellerEmail 等已实证在库内数据中），P1 窗口期新表即明文积累 GDPR 个人数据，稿自称 PII 是"必须随方案落地"却把落地排在首写之后；②既有 sanitizer 是**敏感字段黑名单掩码**，白名单投影是"只出必要字段"的反方向操作——接线现有件交付不了裁决 5 要求的投影，需要新投影函数+字段清单，而**清单谁定**（D 员报告已给必要集=PCI 10.2.2 六要素+资源标识）稿未指定责任方；③"存在但未接线"表述半不准：sanitizer 已注入 `security.middleware.ts:10`（中间件本身从未 `.apply()`）与 `payment-security.service.ts:270`（该服务无任何注入点=死码）——未接的准确说是"审计/事件落库链路"，实施者按稿面去找"未接线"会找错改点。
- 理由：硬边界项的时序+交付物定义+事实定位三处错位，任何一处都会让 P2 施工跑偏。

**F6｜"同事务 INSERT"的写路径事务底座盘点缺失；退款双列于 P1/P3 边界不明**
- 位置：§3 图（"INSERT event_outbox 行（无链列，同事务）"）、§4 P1（"订单/商品/退款路径挂 INSERT"）/P3（"退款事件补全"）；对照 C 员 13 条写路径总表：仅 W1/W2/W3/W7 有显式事务；W5（商品更新=互斥包两段 autocommit 写段）、W6（商品建删=单语句 autocommit）、W8/W11（支付单创建/关闭）、W12（退款，`payment\application\services\payment-application.service.ts:371-449` 实读 0 mutex/0 事务/0 audit）全部无事务可"同事务"挂靠。
- 实操影响：outbox 的原子性前提是"业务写与事件行同一显式事务"——对已有事务的订单路径近似零成本；对商品/退款/支付路径则**必须先引入显式事务并入队 `runExclusiveWrite`**，这是热点路径的结构改造（延迟、队列压力、W12 六百行函数的事务化），改造量与风险方案零着墨。且退款同时出现在 P1（挂 INSERT）与 P3（事件补全）两行，同一工作两个阶段归属，实施者无从切分。
- 理由："同事务"三字对 13 条写路径中的 9 条不是挂一行 INSERT 而是先造事务底座——工作量被稿面隐藏。
