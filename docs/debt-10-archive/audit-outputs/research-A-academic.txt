## 节 1 · append-only 保证的机制谱系

三条路线，保证“不重写”的机制各不相同：

**(a) 协议层（RFC 6962）**：append-only 不是存储特性，而是由**外部监督结构 + 密码学证明**强制的不变量——第三方 witness 持有旧 Signed Tree Head，新树必须出具一致性证明证明旧树是新树的前缀，否则分叉可被任何持有两个 STH 的观察者发现。canonical 化规则（叶 0x00 / 内点 0x01 前缀域分离）**冻结在 RFC 正文里**，从第一天起就不可由实现者事后更改。

**(b) 摘要结构层（Crosby & Wallach 2009；QLDB；GlassDB）**：不可重写的**证明效率**取决于摘要结构。线性哈希链的包含/一致性证明是 O(n)；history tree（Merkle 树）降到 O(log n)。QLDB 把这个结论产品化了：官方文档明说“ledger 增长后全链重算验证低效，所以用 Merkle 树”。

**(c) 存储引擎层（Oracle Blockchain Table；Azure SQL Ledger；immudb）**：引擎在 API 层直接阻断 UPDATE/DELETE（"block updates and deletions at the API level"），哈希在**行插入的那一个事务内**由引擎计算，canonical 规则由引擎二进制独占——应用层没有任何代码路径能触发对已落链数据的重算。

**对问题 4（重锚反模式）的教益**：全部 12 个系统没有一处靠“改 canonical 规则后全表重算”来演进。三条正路：① 规则冻结在协议/引擎里（RFC 6962 / Oracle / Azure）；② 内容确需事后变更时，**链结构不动、只换数据位**（QLDB redaction：数据替换为其哈希、序列号与元数据原样保留，证明仍验证）；③ 规则确需换代时，**追加新纪元 + 跨纪元一致性证明**（CT 的 consistency proof 天生就是“证明旧承诺仍是无误前缀”的工具）。已发生 2 次的全表重算在任何被引系统中都没有先例。

## 节 2 · 审计与业务解耦的文献模型

谱系两端加一个中间态：

- **审计独立于业务（CT）**：log 是独立网络服务，业务（CA）异步提交，monitor/auditor 事后核对。审计永远不在业务事务的关键路径上。
- **审计即业务库（QLDB）**：journal 是**唯一**真源（"Each ledger has exactly one journal"），一切“表”都是投影——系统中根本不存在第二条可冗余的链。
- **库内 ledger 表（Oracle / Azure）**：业务行与审计保证**同事务原子生效**，哈希由引擎算——审计写不可能在业务提交后单独失败，fail-closed 是构造性属性而非策略开关；也不存在应用级第二把互斥锁（对问题 2 的直接回答：文献中没有任何系统在业务事务内同步调用第二个自带互斥与事务的服务）。
- **Fabric**：execute（背书）与 validate（含审计性检查）分离——验证在写路径内但与业务执行解耦，ordering service 批处理。
- **Event sourcing（Overeem）**：日志是 source of truth，状态是派生物——审计与业务天然单链单写。

**对问题 1（双链冗余）的教益**：CT 明文“一条单树”，QLDB 明文“恰好一个 journal”——文献一致答案是一条全局日志 + 派生视图/映射。两条平行哈希链、其一零消费，在被引的全部系统中无先例；Crosby & Wallach 更进一步论证纯哈希链本身连“低事件量以外”的场景都不胜任。

**对问题 3（fail-open/closed 矛盾）的教益**：文献把这个问题识别为威胁模型而非实现细节——Hicks SoK 列出的典型威胁之一就是操作者用“编辑控制”把特定事件排除在日志外（逐字引文见卡 7）。本仓同一函数既 fail-open 又被提案要求 fail-closed，等价于把“编辑控制”留给了实现者的运行时错误。文献的两条出路：要么引擎内一体（fail-closed 免死锁），要么业务外异步（CT monitors，接受最终一致）——没有第三条“事务内同步调用外部审计且失败不回滚”。

## 节 3 · 验证与对账的文献模型

- **CT**：验证三件套 = STH（对 root+tree_size 的签名承诺）+ 一致性证明（证明只追加不删改）+ 包含证明（单条 O(log n)）。审计者不需要全量数据。
- **QLDB**：digest（外部可信处保存）+ GetRevision 证明；redaction 之后证明仍可验证。关键句：digest 必须存在 QLDB 之外才构成证据。
- **Azure SQL Ledger**：digest 必须外置不可变存储（理由逐字入卡：攻击者若能改 digest，重算即可掩盖）；验证 = 拿历史 digest 对当前状态重算比对。且承认引擎内防线对“控制机器的管理员”不成立，只剩**可检测性**。
- **数字对比（Crosby & Wallach）**：8000 万事件的日志，单事件包含证明——哈希链要 800MB，history tree 只要 3KB。
- **GlassDB**：把验证效率当一等公民（证明结构 + 并发批量），并把 QLDB/CT 类系统归为“只有 KV 接口、缺事务、验证低效”的基线。

**对“每单一链森林”（问题 1 的验证面）的教益**：森林的验证成本 = 链数 × 链长（线性），且**森林没有跨链一致性证明**——删掉一整条单链在纯哈希链森林中不可检测。CT 的一致性证明恰好就是防“整段日志消失”的机制（证明新树包含旧树全部叶子）。本仓 R1-R4 对账若走全局单树 + 各单包含证明，可同时获得 O(log n) 与防整链删除两个性质。**对问题 5（多态 FK）的教益**：Oracle 用三元组 (instance_id, chain_id, sequence_id) 定位链上行——链身份天然带类型维度；CONIKS 类 prefix tree 用键类型化命名空间；SQL:2011 时态列由系统 `GENERATED ALWAYS` 生成、应用不可伪造。审计行 entity_id 单 int 无类型标记，在这三种模型中都无处安放。

### 卡 1 · RFC 6962 "Certificate Transparency" —【相关性：高】
Laurie, Langley, Kasper（Google）· 2013 · RFC 6962（Experimental）· 检索日期 2026-10-14 · **全文精读**（rfc-editor.org 纯文本）
核心机制：CA 证书进单棵 append-only Merkle 树；叶哈希 0x00 前缀、内点 0x01 前缀（域分离，防跨结构哈希歧义）；树头（root + tree_size）定期签名成 STH；客户端用包含证明对任一 STH 验单条目，用一致性证明验证新旧 STH 间只追加。canonical 规则全部写在 RFC 正文。
逐字引文：
> "A log is a single, ever-growing, append-only Merkle Tree of such certificates."（§3）
> "Merkle consistency proofs prove the append-only property of the tree."（§2.1.2）
> "MTH({d(0)}) = SHA-256(0x00 || d(0)). ... MTH(D[n]) = SHA-256(0x01 || MTH(D[0:k]) || MTH(D[k:n])),"（§2.1）
另："Each log MUST produce on demand a Signed Tree Head that is no older than the Maximum Merge Delay."（§3.5）
问题映射：**P1**（单树是规范用语，双链无先例）· **P3**（append-only 是协议不变量，不是服务自身承诺）· **P4**（canonical 规则冻结在 RFC，无处“改规则重锚”）。
