## P0-B 触发器重设计独立推演

**[P0-B-1｜P0] 触发器豁免窗仅覆盖"补链"半程，"翻 INLINE"在翻完后被 ABORT**
v5.2 §0.1 SQL（line 26-32）：
```sql
CREATE TRIGGER deny_chained_update BEFORE UPDATE ON domain_events
WHEN OLD.seq IS NOT NULL
BEGIN SELECT RAISE(ABORT, 'chained rows are immutable'); END;
```
H 员任务书对照基准（research-H-source-compare.txt:178-184）描述的类 2 生命周期是 **INSERT PENDING → 异步腿补链（填 seq/prevHash/recordHash）→ 翻 INLINE**，翻 INLINE 是单独的 relayState 变更。两阶段两种 UPDATE：

| 步骤 | OLD.seq | 触发器判定 | 结果 |
|---|---|---|---|
| 补链 UPDATE（填 seq/prevHash/recordHash，relayState 仍 PENDING）| NULL | OLD.seq IS NOT NULL = false | 放行 ✓ |
| 翻 INLINE UPDATE（relayState PENDING→INLINE）| 已是值 | OLD.seq IS NOT NULL = true | **ABORT ✗** |

**修复仅覆盖第一步**。v5.2 §0.1 措辞"补链/中继元数据 UPDATE 放行"——"中继元数据"含糊到包含 relayState 变更，但技术上当 seq 已填好、OLD.seq IS NOT NULL，翻 INLINE 的 UPDATE 即 ABORT。独立实现路径——若补链与翻 INLINE 是单条原子 UPDATE（同时填 seq 与翻 relayState）——豁免窗正确；但 v5.2 未规约"翻 INLINE"必须与"补链"原子合并，且 H 员对照基准明示分两步（"补 seq/prevHash/recordHash、翻 INLINE"），则原班分步实现路径被本触发器直接瘫痪。**同类未抓实例复发**——v5.1 数据路 F-2 抓"全面 ABORT"半面，v5.2 修复抓"补链豁免"半面，"翻 INLINE"半面仍是 ABORT，无人抓。

**[P0-B-2｜P0] payment_refunds 在 TiDB 形态下的 DB 级保护=0**
v5.2 §0.1（line 33）："TiDB 形态：无触发器——append-only 改由 **DB 权限**承担（应用账号 `GRANT INSERT,SELECT ON domain_events` + 不授 UPDATE/DELETE……）"
v5.2 §0.1（line 34）："payment_refunds 撤下'同款'……该表完整性由条件 UPDATE 协议（规格 c）+ 域事件链间接承载"

TiDB 形态推演：
1. payment_refunds 是状态机表，六分类处置（→CONFIRMED/FAILED/NEEDS_REVIEW、attempts+1、gatewayRefundId 回填、勘误 #12 的人工裁决 UPDATE 端点）全是 UPDATE——**应用账号不能"不授 UPDATE/DELETE"于 payment_refunds，否则状态变迁瘫痪**。
2. v5.2 只规约了 domain_events 的 GRANT，但 payment_refunds 必须 GRANT UPDATE/SELECT/INSERT 给应用账号——即任何有权 UPDATE payment_refunds 的应用账号都能直接绕过规格 c（"UPDATE ... WHERE status='PENDING_GATEWAY'" 的 WHERE 子句是应用纪律，不是 DB 强制）：`UPDATE payment_refunds SET status='FAILED' WHERE id=X` 合法执行。
3. v5.2 §0.1 的"条件 UPDATE 协议（规格 c）+ 域事件链间接承载"——规格 c 是应用层协议，DB 不强制；域事件链只能事后证明"REFUND_CONFIRMED 事件存在"，不能证明事件与 payment_refunds 行的因果锁链（攻击者可同时改行+插伪造事件）。
4. TiDB 形态下没有"妥协管理员/ORM bug/SQL 注入"的 DB 级兜底——这恰是 H 员 §1.6 引 aegis 触发器注释（research-H:119）所堵的三类威胁。

**结论**：v5.2 把 payment_refunds 从"DB 级保护"降级为"应用纪律 + 旁路审计链"，**未在 §0.1 显式承接该降级带来的威胁模型变化**——"防 DBA 级"在 payment_refunds 表上不成立，且 sqlite 形态的触发器也未挂该表（撤下"同款"），则 sqlite 形态下 payment_refunds 同样无 DB 级保护。规格 c 协议+审计链是 v5 的两条腿，撤掉 DB 触发器后这两条腿外**无第三道 DB 防线**。

**[P0-B-3｜P2] "双方言各一形"对 sqlite 形态实为"两触发器形"，v5.2 表述含糊**
v5.2 §0.1（line 33）："'双方言各一形'重写为'sqlite=触发器形 / TiDB=权限形'"
