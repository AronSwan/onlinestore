## 一、分腿设计内部一致性（v2 最大变更）

### 1a. 类 1/3 同事务一步链化 —— **推演结论：成立，无循环依赖，C2/C3 相容。P3×1**

**无循环依赖**：recordHash 的 11 个 canonical 输入（§3.3 键表）中，seq/prevHash 来自链头读，其余 9 个为应用侧值——全部在 INSERT 前可知，无任何列值依赖本行 DB 生成值。DDL 中 DB 生成值仅 id（AUTOINCREMENT）与 created_at（DEFAULT CURRENT_TIMESTAMP），二者均不在 canonical（§3.2 行注+§3.3 排除清单）。时序 读链头→seq=prev+1→算 hash→INSERT 全列 是无环的。

**C2 相容**：链化写在调用方事务内、调用方事务在 runExclusiveWrite 内，全程零次新增取锁——与 appendSnapshot 已验证的形状（order-snapshot.service.ts:116-206，C8 同事务纪律）同构，不触 db-write-mutex.ts:26 嵌套禁令。W7 死锁病灶（log() 自带第二 mutex+第二事务，audit.service.ts:202-218）不在此路径上。

**C3 相容**：单写者下链头读与 INSERT 同互斥段串行，无竞争（v2 “同构于现行 W7” 表述与 audit.service.ts:204-208 一致）；多实例下 seq 唯一索引（§3.2 `idx_domain_events_seq`）兜底整笔回滚，且 T2 已以分歧保留形式承认多实例下 B 员外移更优——多实例边界是已声明的取舍而非漏洞。

**[F-09｜P3] id 不入 canonical 的理由未成文**：老链 canonical 含 id（audit-chain.ts:22-38，16 键含 'id'），id 是 DB 生成值——若照抄入新 canonical，一步链化立即不可能。v2 恰好没放 id 进键表（正确），但 §3.2/§3.3 对这个与 occurredAt 同类的必要条件只字未提；T2 论证只讲了 Date 半边。将来若有人“补全”id 入 canonical，一步链化静默失效。建议一句通则成文：“DB 生成值（id/created_at）一律不入 canonical”。

### 1b. 类 2 PENDING 行补链 —— **任务书点名的深洞：正确算法下不存在 seq 冲突，但承重算法未成文。P1×1 + P2×1**

**独立推演结果（回答“窗口里 INLINE 行读到什么/seq 是否被破坏”）**：
- DDL 行注钉死 “链列（PENDING 行 NULL；INLINE 行一步写入）”（§3.2 seq 列注）——即禁止 INSERT 时预分配 seq。
- 在此约束下，INLINE 行的链头读（谓词须 `WHERE seq IS NOT NULL ORDER BY seq DESC LIMIT 1`，同 W7 原文 audit.service.ts:205）**读不到 PENDING 行**（其 seq 为 NULL）——窗口内 INLINE 行在现行链尾后续链，seq 单调推进，不跳号。
- PENDING 行补链时取**当时**链头+1：中间 INLINE 行占掉的号是“当时的头”，PENDING 行排在其后拿新号。任务书假设的冲突场景（“PENDING id 小但中间 INLINE 占号→补链撞唯一索引”）只在**插入时预分配 seq** 的错误实现下发生，而该实现已被 DDL 行注排除。sqlite/MySQL 唯一索引均允许多重 NULL，PENDING 积压不撞索引。
- **结论：无结构性 seq 冲突**。但代价是类 2 行的链序=补链序≠发生序（先发生的类 2 事件链在后的类 1 事件之后）——对链完整性无碍（verify 按 seq 验链不按时间），对“时间线查询”消费方有语义影响（须按 occurred_at 排序而非 seq）。

**[F-01｜P1] 类 2 PENDING 行的 INSERT 时机未交代——分腿设计在关键节点上不可判定**。§3.1 类 2 分支全文：“业务事务 COMMIT 后 → EventEmitter2 fire-and-forget（现行 census⑤ 模式不变）→ 异步腿 worker：读 relayState=PENDING 行 → 补链列”——**图中没有 INSERT 步**。两种读法：
- 读法 A（好）：业务事务内 INSERT PENDING 行（链列 NULL，relay_state 显式 'PENDING'，DDL 默认值 'INLINE' 说明须显式传入）、commit 后 JIT drain 只补链。此为 outbox 正统：存储 fail-closed、送达 fail-open，重试腿有持久物可重试。
- 读法 B（坏）：commit 后 fire-and-forget 时才插行。则 COMMIT 与 INSERT 之间进程崩溃=事件永久丢失且**重试机制无物可重试**（兜底轮询扫表扫不到从未插入的行）——这正是 M5/R3 病灶（fail-open 永久缺失，D 员 Q2 判其踩 10.2.1 覆盖义务）在类 2 上的残留。

文本倾向哪边？T5 裁决原文“类 2=异步腿（**fail-open**+重试+死信+告警）”把 fail-open 标到整腿（含存储），字面支持读法 B；但 T5 同句引“B 员分层”为来源，而 B 员分层教义（research-B §二）是“存储内带 fail-closed **+** 送达外带 fail-open”两条腿、存储侧不分事件类。**v2 的两个来源互相打架，方案正文不含裁决所必需的那一句 INSERT 位置**。类 2 腿在 P1 就上线（§4.1），此洞不是远期问题。修复只需一句：“类 2 行由业务事务同事务 INSERT（relay_state='PENDING'，链列 NULL）；异步腿只补链列+翻 INLINE”——但按 v2 自立的“技术前置件补齐”标准（v1 正因“五大构件停在命名层”被判不可用），这句是承重件，缺失即立案。

**[F-02｜P2] 异步腿补链算法三要素未成文**：(i) 链头读谓词须排除 seq-NULL 行（W7 有先例、v2 未重述）；(ii) seq=补链时点链头+1、禁止预分配（DDL 行注隐含、算法层未写）；(iii) 多实例下的行认领语义（F 员 C11 已示范条件 UPDATE `tryClaim` 模式，§3.4 参数表未收；R2 双触发每实例一份，多实例重复 drain 无认领约定）。另类 2 链序≠发生序对时间线消费方的影响（见 1b 推演）全文零交代。三项均可由胜任实现者推出，但 v2 的自我定位是“命名层→前置件”的升级稿，承重不变式应落在纸面。

### 1c. relay_state/attempts 的 UPDATE 是否破链 —— **结论：不破，机制正确；交代半句。P3×1**

canonical 11 键不含 relayState/attempts/lastError（§3.3 明列排除）→ 补链 UPDATE（PENDING→INLINE+写链列）发生在 hash 计算同时或之前；链化后这些列的任何再 UPDATE 都不触碰 canonical 输入，recordHash 保持可复算。时序上也无矛盾：INLINE 后不再有 attempts 递增（行已出队）、DEAD 行 seq 恒 NULL 无 hash 可破、payload 可删（b 变体 erasure 位）而 payload_hash 是锚不删——验证侧重算不受影响。**[F-10｜P3]** v2 写了排除清单但没写收尾句“中继列 UPDATE 不影响已算好的 recordHash”——一步推理可补，属成文完备性缺口。

## 二、b 变体语义边界：R3'/R4 是否失去明文验证能力 —— **确有缺口，v2 只交代了备份面、漏了在线面。P1×1**

**[F-03｜P1] 在线明文区完整性无任何机制覆盖**。链条推演：
- 链只锚 payloadHash=HMAC(payload)（§3.2/§3.3），payload 明文不在 canonical。攻击者改 DB 中 payload 明文而不动 payload_hash：链全绿、verify 零告警——**篡改检测能力对 payload 列为零**。这不是抽象威胁：本仓链的存在理由就是防篡改检测（D 员 10.3.4 变更检测义务的可接受措施）。
- E 员原文对选项 b 明言此缺口并给出要求：“链外明文的完整性不再被链保护（**需快照一致性另立机制**）”（research-E 选项空间表 b 行）。
- v2 的交代盘点：§2 T3/T4 分歧保留只列“a/e 对备份/冷区副本覆盖更彻底……b 的明文区**备份副本**是残余风险”；§6.1.3 同样只列备份副本。**在线明文区的“另立机制”在 §3.8 四条对账（R1'/R2/R3'/R4）、§4 验收、§6 未决三处均无踪影**。
- 该机制其实现成可用：对未擦除行重算 HMAC(payload) 与存量 payload_hash 比对（一条 SQL 级对账腿，兼验白名单投影未被绕过），可挂 R3'。v2 未立。备选修复：明文区完整性腿（HMAC 重算）入 §3.8 并在 §6.1.1（key 轮换会使旧行 HMAC 重算失效）挂关联未决。

R4（链头→git 外锚）本身锚的是链头摘要，对明文区同样无覆盖——与“定时外锚未定”（§6.1.4 已挂账）是两回事，不能互相顶替。

## 三、§2 T2 裁决的技术论证质量 —— **occurredAt 字符串化消除 C6 的推论链成立；两处半成品。P3×2**

**核心推论验证（扎实）**：C6 原文（research-C §五 C6）＝“哈希字节=驱动原生行回读（防 Date 往返漂移）→两步写是结构必然”。两步写的存在理由是 canonical 含 Date 值（老链 createTime，audit.service.ts:188 传 `new Date()`；快照链 occurredAt/snapshot 同理，order-snapshot.service.ts:181-198 须回读并做字符串矫正）。新表 canonical 11 键中：occurred_at CHAR(19) 应用生成定长字符串（§3.2 行注“不入 DB Date”）、payload_hash/prev_hash CHAR(64) hex、其余 VARCHAR/整数——**无一 Date 型、无一 JSON 列入 canonical**。字符串列在 sqlite（TEXT）与 MySQL 协议（CHAR）两侧逐字往返，无驱动归一化歧义 → 写侧应用值=存库值=验侧原生行值，回读失去必要性 → 一步写成立。推论链每一环核过代码，成立。

**任务书追问的 payload JSON 往返漂移**：确认不影响链——payload TEXT 不在 canonical，链上只有 HMAC；即便驱动对 JSON 文本做往返变形，也只是（未存在的）HMAC 重算腿的假阳性面，链完整性不受触碰。快照链当年为 JSON 列做的字符串矫正（order-snapshot.service.ts:193-197）在 v2 里因 payload 出 canonical 而结构性地不需要——此点 v2 未点破但设计正确。

**半成品两处**：
- **[F-09｜P3]**（同 1a）id 排除未说明——老链 canonical 含 id 是一步写不能照抄的另一半理由，T2 论证只覆盖 Date 半边。
- **[F-11｜P3]** §3.1 哈希公式记法 `recordHash=H(canonical‖payloadHash)` 与 §3.3 键表自相打架：payloadHash 已是 canonical 第 9 键，公式再拼接一次=重复计入；且现行实现是 `SHA256(prevHash\n + canonical)` 前缀式（audit-chain.ts:94-95）而 v2 公式无 prevHash 前缀（canonical 含 prevHash 键，可行但与复用的“anchor 机制/verify 脚本”字节格式不同族）。键表应为权威、公式应改写，否则送审轮会再抓一次“命名层”。

T2 对 B 员碰撞缺失的自我标注（“此裁决未与 B 员原文碰撞——分歧保留”）与 B 员原文（research-B §一结语“链化/验链/告警全部移到事务外的中继侧”）核对属实，标注诚实。
