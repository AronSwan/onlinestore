## 一、T9 规格推演（重点项）

**[L4-01｜P1] 规格 a 收窄后状态机漏第四出口——“持续不决”无终态、attempts 满后行为未定义、无告警纪律**。规格 a 定义的三态（§3.9 status 注：PENDING_GATEWAY/CONFIRMED/FAILED）收窄 FAILED 后产生新路径：歧义错误与“回查不决”都留 PENDING_GATEWAY 交扫描，而扫描自身可能永远不决（网关持续返回 unknown/查询键缺失见 L4-02/回填事务持续失败）。v4 补了 attempts/lastError 列但仅标注“扫描退避依据”（§3.9）——**满 attempts 后落什么态无定义**：domain_events 腿有 relayState='DEAD'+告警（§3.4/判据 3），payment_refunds 腿对称件只补了两列没补终态与死信行为；§6.1-9 的“人工对账兜底”仅覆盖“网关无查询能力”情形，不覆盖“查而不决”。后果链：规格 b 规定 PENDING_GATEWAY 计入保留额（保守方向正确，无超退）→ 但永久占额 + 无出口 + 无告警 = 该支付单可退余额被无限期冻结（活性缺口，且无人知道）。修复方向：定义第四态（如 NEEDS_REVIEW）或“attempts 达 N 冻结扫描+告警+人工裁决”成文，并写明该态在守卫的计入语义（应计入——保守）。

**[L4-02｜P1] 规格 c 条件转换协议本身正确，但其输入端（回查键形状+查询结果裁决表）未定义——误归因与误分类两条路都能穿透协议**。协议推演：同源网关真值下，事务 2 与扫描的竞争由 `UPDATE … WHERE status='PENDING_GATEWAY'` 决胜，胜者插事件、败者 affected=0 跳过——无重复事件、无双终态，**协议自洽**（含“网关查询读延迟→not-visible 应归歧义类不落 FAILED”的情形，前提是分类纪律存在，见下）。缺口在其承重前提：①**查询键形状**——三审 P1-2 原文明言“崩溃点若在 gateway.createRefund 调用前 gatewayRefundId=NULL，回查键只剩 paymentOrderId+refundId——连查询键形状都没定义”；v4 §1.2 行 6 声称已响应（规格 c/d + §6.1-9 前提），但 §6.1-9 只升级了“方法存在性”，键形状全文仍零字。按 paymentOrderId 查可命中**同支付单另一笔退款**的状态→误归因 CONFIRMED/FAILED 到本行→条件 UPDATE 先胜→事务 2 持真实结果静默败退（affected=0）→终态错+事件错。②**查询结果裁决表**——“网关查询不可见”（读延迟/传播中/未创建）与“网关明确拒绝”必须分账：前者归歧义留 PENDING，后者才落 FAILED；v4 未写此分类纪律，若实现者把 not-visible 误分类为拒绝→FAILED→释放配额，而网关侧实际在途成功→规格 a 要堵的“误判 FAILED→超额退款”从扫描腿回开。另外 payment_refunds DDL 无退款域标识列（id 为自增整数，见 L4-06），三审所说“paymentOrderId+refundId”键中的 refundId 在表内无承载列。

**[L4-03｜P2] 规格 a 的实施面（错误分类维度）未排产**。现行 `GatewayResult = {success, data?, message?}`（backend/src/payment/common/gateway-result.ts:1-8）无错误类别维度，适配器对 `!result.success` 一律 throw 打平（strategy-gateway.adapter.ts:131-133，v4 引 ：128-131 微偏）——规格 a“FAILED 仅收网关明确拒绝”要求策略层返回可分类结果（明确拒绝/歧义）且适配器不再打平。§4.1 P2 行只点名“queryRefundStatus 接口方法+4 策略实现”，分类接口扩展+4 策略改造+适配器改写三件无行。与三审 P1-8（排产件隐身）同类，但规格 a 语义可倒推出该需求，故 P2 不升 P1。

**[L4-04｜P2] 规格 e“读写同切（同一 commit）”是代码原子性，不是运行时原子性——切换工序次序未写；存量行状态映射未定义**。任务书假设的矛盾（“切换日前新表已积累 PENDING 行而守卫还读旧源”）**经独立推演不成立**：v4 方案下 P1 只建表、P2 切写即切换日，切换日前新表零写入，“两个 PENDING 计入时机”无双源并存窗——切换边界的代码层自洽性验证通过。真实缺口：①“同一 commit”只保证三处代码同版；运行时切换工序（停旧写→迁移存量→对账核对→开新写）的**次序**未成文——若迁移脚本快照后旧路径仍在产 metadata.refunds 行（部署重叠/停机不彻底），该行不入表→守卫失明→超退，恰是 v4 自引的 W-3 失明模式（typeorm-payment-order.repository.ts:265-267 注释实锚）；过渡期对账腿（已入 P2 行）能事后抓但超退可能已发生。②dev 存量行实测（复现：`sqlite3 backend/data/dev_caddy_shopping.db "SELECT paymentId,metadata FROM payments WHERE metadata LIKE '%refunds%'"`，2026-10-13，口径=dev 库，命中 1 行）status=**'PENDING'** 且带非空 gatewayRefundId（REFUND_ALIPAY_…）——旧词表值迁移到三态词表映射到哪一态未写（合理缺省=PENDING_GATEWAY 交扫描用 gatewayRefundId 回查裁决，但须成文；映射到 FAILED 即释放配额，方向错误）。生产切换存量回补另挂 §6.2-12 未决（已露面，合规）。

**[L4-05｜P3] 规格 d 推演通过；一处小缺**。互斥段组成=条件 UPDATE+读链头+事件插行，段内无网络 I/O ✓；事件插行按 §3.1 API 契约骑调用方 EntityManager→与条件 UPDATE 同事务→插事件失败整体回滚→行留 PENDING_GATEWAY→重扫幂等，无“态转了事件丢”窗口 ✓；链头读在写队列内见最新已提交头 ✓；双扫描实例互斥外重复查询网关无害（条件 UPDATE 决胜）✓。小缺：规格 c“payment_refunds 扫描腿与 domain_events 腿各自 tryClaim”——payment_refunds 无 relayState 列，认领谓词（status='PENDING_GATEWAY' AND attempts<?？）未写。另与 L4-01 咬合：回填事务持续失败→无限重试无上限。
