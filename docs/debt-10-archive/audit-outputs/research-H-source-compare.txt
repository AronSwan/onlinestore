## 二、tamper-audit（Rust crate v0.2.0，仓库=WyattAu/auditlog）

### 2.1 链实现：read-tip→construct→append，竞态不设防

`src/log.rs`（255 行，本地缓存核对 docs.rs 渲染一致）第 57-66 行逐字：

```rust
let previous_hash = self
    .store
    .last_entry()
    .await?
    .map(|e| e.hash)
    .unwrap_or_else(|| "0".repeat(64));

let entry = AuditEntry::new(actor, action, resource, details, &previous_hash);
```

`last_entry()` 与 `append()` 之间**无锁、无事务**；`InMemoryStore` 的 `std::sync::Mutex<Vec<AuditEntry>>` 只护单次操作，两个并发 append 可读到同链尖→同 prev_hash→**分叉**。

### 2.2 Postgres 后端同样裸奔

`src/postgres.rs`（142 行，feature "persistence"）append 就是裸 INSERT（第 88-90 行：`"INSERT INTO audit_entries (id, timestamp, ...) VALUES ($1,...)"`），无事务包裹 tip 读取、无 FOR UPDATE、无 advisory lock。`last_entry` 用 `ORDER BY sequence DESC LIMIT 1`（表有 `sequence BIGINT GENERATED ALWAYS AS IDENTITY`）。migrate=`CREATE TABLE IF NOT EXISTS`，**无版本化迁移**；`ensure_genesis` 的 count 检查与插入不在同一事务（双 open 并发可插双创世）。

### 2.3 哈希：7 字段裸拼接，两个真实弱点

`src/entry.rs`（docs.rs 渲染，检索 2026-10-13）`hash_data()` 把 id/RFC3339 时间戳/actor/action/resource/details/prev_hash 字节**直接拼接，无分隔符无长度前缀**（相邻字段边界碰撞理论可行）；details 序列化失败静默吞掉：

```rust
data.extend_from_slice(
    serde_json::to_string(&self.details)
        .unwrap_or_default()
        .as_bytes(),
);
```

坏 payload 哈希后等价于空串。无 RFC8785 规范化，RFC3339 允许同时刻多种表示。

### 2.4 验证：线性单链检查，无分叉检测

`src/verify.rs`：逐条 `verify_hash()` 重算 + 与前一条 hash 比 prev_hash（失败消息"previous_hash '{}' does not match entry {} hash '{}'"），**不检同 prev_hash 分叉、不检重复哈希、无签名无时间戳检查**——2.1 的分叉在此大概率验不出来（后插入的分叉支整段通过）。

### 2.5 质量评估

代码干净、100% 文档化、测试覆盖链与篡改检出，但它是 v0.2 单人 crate：**并发、持久层竞态、演进全部未解**。可借鉴的只有“store trait 抽象”这一层形状，实现不可照搬。

## 三、transparency-dev/tessera（Go，任务书降级项——两主目标均可达，本节仅做类 2 同构度快照）

`entry.go`（80 行）第 56-58 行注释是类 2 异步腿的工业级表述，逐字：

```go
// MarshalBundleData _may_ be called multiple times, potentially with different values for index
// (e.g. if there's a failure in the storage when trying to persist the assignment), so index should not
// be considered final until the storage Add method has returned successfully with the durably assigned index.
```

写入接口形状（`append_lifecycle.go` 第 523 行）：`func (t *terminator) Add(ctx context.Context, entry *Entry) IndexFuture` —— Add 立即返回**可等待的未来**（解析为持久分配的 index），Shutdown 契约原文：“all calls to Add that have returned a value will be resolved… integrated and have a checkpoint that commits to them published”。树构建/检查点发布完全后台化，等待方用 PublicationAwaiter 轮询 checkpoint。**与我们类 2 的 INSERT PENDING→异步补链→翻 INLINE 同构**：PENDING 行≈未解析 future，INLINE 翻转≈"durably assigned index"，等价物是 Shutdown 的排空契约（所有已受理写必须最终落树）。

## 五、“我们没想到的”清单

1. **DB 级 append-only 触发器**（aegis 3a519b48a6f2）：BEFORE UPDATE OR DELETE raise P0001。防的是“妥协的管理员/ORM bug/SQL 注入静默改删链行”——把不变量从应用纪律移进数据库。故意绕过须同事务 DROP TRIGGER 并记 runbook+并入下一 Merkle 根。本仓 sqlite 可用 `PRAGMA` + 触发器同款实现，成本一行 SQL。
2. **日频 Merkle 根跨日链 + 包含证明**：即使攻击者重写整库（重算全链），客户留存的日根对不上即可检出**整库替换**——这是纯哈希链给不了的对抗等级（哈希链只能检出“改了没重算全链”的攻击）。
3. **验证结果指标化**：`AUDIT_CHAIN_VIOLATIONS_TOTAL.inc()` 放在 return 之前，“即使下游吞掉响应体，告警页也已触发”。本仓 verify 目前只给人看。
4. **离线证据 bundle 的保留期诚实度检查（V6）**：声称“保留 6 个月”而 bundle 最早行>6 月=宣称不诚实。审计合规向的巧检查。
5. **密钥轮换迁移带历史回填**：s18 迁移从每行存的 public_key_pem 重算全史指纹，“existing signatures still verify”——轮换不废历史。
6. **空树哨兵根**：`sha256(b"")`，区分“今天没有事件”与“事件丢了”。
7. **幂等双保险的形状**：partial unique index（WHERE request_id IS NOT NULL）+ ON CONFLICT DO NOTHING + 重复计数器——双实例竞态下链不脏。
8. **tessera 的 index 终局性原则**：“index 在存储 Add 持久成功前不算最终值”——本仓类 2 的 INLINE 翻转应视为同一原则，宜在文档里明说“seq/链列在补链腿成功前不是事实”。
9. **空链判定**：“an empty chain is integrous by definition”（aegis 2026-05-13 修的坑：曾返回缺字段导致 UI 真值判断塌成 broken）。

## 六、“它们踩过的坑”清单（全部来自源码 dated 注释）

1. **H-4（2026-05-13）哈希计算曾在锁外/库外**（Redis 路径）→ 移入 advisory lock 事务内。教训：链头读取与哈希计算必须在同一串行化域。
2. **v5-Fix（2026-07-25）advisory lock 下仍现链 gap**（shards 8+12，>50rps）——疑似 pgbouncer 事务池与连接级锁语义互作，**未根因**，叠 Redis 锁防御。教训：连接池环境下锁语义要实测，别信文档。
3. **C-3：验证器重算了哈希但不比对**（恒过）。最危险的一类坑——验证器存在≠验证发生。本仓 verify 应有“故意篡改样例必须报红”的自检腿。
4. **P0（2026-05-04）异步计费模式压测孤儿审计 5,926 条**→改同步+超时兜底。教训：异步腿要有压测证伪。
5. **Gap 3（2026-05-15）同步路径与 outbox 用了不同 audit_id**→UNIQUE 约束永不触发，双行。教训：幂等键必须收敛到同一定义源。
6. **ORM 声明 DB-only 默认值列在 pgbouncer 下炸 asyncpg 预编译缓存**→chain_sequence 刻意不进 ORM。教训：外部验证器消费的列与 ORM 解耦。
7. **128 位截断指纹**：“没有成本节省，白减碰撞余量”→全量回填。教训：截断要有理由。
8. **tamper-audit：`unwrap_or_default()` 吞序列化失败**——坏 payload 哈希等价空串，静默。
9. **aegis 验序漂移**：建链=插入序，integrity.py 按 (timestamp,id)，aevf 按 timestamp 字符串，models 注释宣称 chain_sequence——四处三种序。DLQ 重放旧时间戳事件即假阳性 gap。教训（直接命中本仓）：**验证排序必须与建链排序同源**（本仓 seq 即此用，务必让 verify 按 seq 走，勿按时间戳）。
10. **10k limit 无续页**：OOM 防护做成了验证覆盖截断。

## 七、反过拟合扫描

- **不引入分片**：aegis 的 16 分片+双锁+Redis 流是**多 worker 横向扩展 Postgres** 的产物；本仓 sqlite 单写者 mutex 下分片纯属负资产。
- **不照搬“never block”**：aegis 业务不等审计是可用性取舍，且付出“响应后崩溃丢窗口”（依赖 Redis 持久化）的代价；本仓类 1/3 原子耦合是既定需求，勿被其反向动摇。
- **不学 aegis 验证器实现**：C-3 旧坑、10k 截断、验序漂移都是反面教材；学它的外围（bundle 版本化/告警直连/V6），不学内核。
- **不把 tamper-audit 当范本**：v0.2 单人 crate，其并发/持久缺陷恰是本仓已解决的问题；仅“store trait 抽象”值得留意。
- **可迁移项（判据=与本仓约束兼容）**：DB append-only 触发器、哈希公式/证据格式版本位、验证器自检腿（篡改样例必报红）、违规计数器直连告警、验证按 seq 排序的明文化。
- 本报告对 G 员三线索的修正均有逐字源码锚（见首节）；aegis 引文以本地缓存文件为准，tamper-audit 的 entry/store/verify 三文件结论来自 docs.rs 源码渲染页（postgres.rs/log.rs 有 GitHub 原文本地核对，二者一致）。
