### 3.2 order_snapshots：每单一链=森林

- **写侧两步写**（order-snapshot.service.ts:161-200）：原生 SQL INSERT 链列 NULL（:163-179）→回读原生行（:182-185，JSON 列保字符串 ：193-197）→computeSnapshotRecordHash（:191）→em.update 补链列（:200）。

## 第六节 问题-约束映射表（3 根因 × 锁死它的约束）

### 根因 1：双链架构本身是债（audit 链从不被 orders 业务用）
- **实证**：audit_logs 1603 行 0 行 module='orders'（2026-10-13 sqlite 实测 products 1523 + audit 80）；ORDER_CREATE 等 8 个订单枚举（audit.service.ts:30-37）**全仓零调用**；AuditService.log 的 module 取值=`context.resourceType||'unknown'`（:176），orders 域从未传 'orders'。
- **锁死约束**：C8（appendSnapshot 明文禁止调 log——order-snapshot.service.ts:13 “自带互斥+独立事务=嵌套自锁死 C 坑A”）+ C2/C6（log 自带 mutex+独立事务，无法嵌入订单事务）→ orders 写路径在结构上**只能**与 audit 链分离。R3（全局存在性版）的“永真告警”是该结构的必然输出（reconcile:138-141）。
- **触发组合**：任何 orders 业务事件（30 单全量）× 现有 log() 形状 → 要么 0 行（现状），要么引渡根因 2 的死锁。

### 根因 2：db-write-mutex 与双写嵌套不可能三角
- **锁死约束**：C2（禁嵌套，db-write-mutex.ts:26）+ C6/C1（log 的链化必须“读头→插→回读→补列”一事务原子，且该事务本身就在互斥内——audit.service.ts:202-203）+ C8（快照必须在调用方订单事务内）。
- **触发组合**【推演，结构必然；13-seats 卷 P0-2 同判】：订单事务（W1/W2，:56/:339 已持 mutex）内部任何点调 `auditService.log()` → log 的 runExclusiveWrite 排在 writeTail 尾（=外层 run 之后）而外层 run 正等待该内层调用返回 → promise 环=永等。v5 提案步 3 的示例代码（debt-10-proposal-v5.md:119-136）恰好把 log() 放进 runExclusiveWrite 的 transaction 回调内——“v5 步 3 必复现 v1 自锁死”。
- **现行代码的规避方式**（即为什么今天没死锁）：审计一律移到互斥块外事后落（W1 :216、W6 控制器层）——这正是根因 3 的 fail-open 来源。支付侧同理：监听器回写在事件（锁外 emit，payment-application.service.ts:350-352）之后重新入队。

### 根因 3：M5 fail-open 与 v5 fail-closed 同函数并存
- **fail-open 语义**【实证】：M5（commit a408615，2026-10-05）在 orders.service.ts:214-244 引入——事务提交后逐条落审计，catch 仅 `logger.warn`；注释 ：215 “订单既已成立，审计失败只告警不回滚”。同哲学先例=商品写审计（products.controller.ts:164-166，M1-B4 2026-10-04）。**前提**：该审计行是“库存归零自动下架”事件（PRODUCT_AUTO_UNLIST），订单本体确已提交。
- **fail-closed 要求**【记载】：v5 提案步 3（debt-10-proposal-v5.md:110-141）——“双写同事务——任意一失败全回滚”，适用类 1（user/admin mutation）与类 3（敏感 admin 动作），与 M5 的类 2（系统派生事件）在同一函数 create()/update() 内并存。
- **锁死约束**：C13（现行 fail-open 是既定纪律）× 根因 2 的 C2/C6（fail-closed 要求 log 入事务=死锁）→ 同一函数内两种语义只能靠“事件分类”区分，而事件分类又依赖 audit 能入事务——三角闭合。13-seats 卷 P0-15 亦判“同 orders 域两套审计哲学=审计员难解释”。
- **附带锁死**：v5 步 2 给 audit_logs 加 entity_id/entityType 列（v5:98-107）撞 C5（键序追加=全链重锚）→“第 3 次重锚必发生”（13-seats 卷 P0-12；前两次重锚见第三节 3.3）。
