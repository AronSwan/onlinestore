## P0（1 项）

### P0-L1 §0 一句话方案对自身设计失真，“三个根因在结构上同时消失”系无限定承重宣称

**位置**：§0（行 12），对照 §1 R1 行（行 20）、§3 裁决 3（行 66）、§4 P4（行 81）、§7（行 107）。

**论证**：三重失真，均可由稿内互证——
1. **“旧双链冻结封存”与正文直接矛盾**。方案实际只冻结 audit_logs 一链（§1 R1 行：“旧 audit_logs 冻结封存”）；order_snapshots 的链列**继续活跃写入**——§3 改造后图明示“appendSnapshot（保留，同事务，业务投影）”，裁决 3 明示其链列降级是“择机”“可分离的后续项”。一句话方案把“半冻结”压缩成“双链封存”。
2. **“在结构上同时消失”采用结构口径而方案交付的是症状口径**。R1 的根因表述有窄（13 席 P0-1：“audit 链 0 行 orders 消费”）宽（方案 §1 自引 A 员判词“双链并行无先例”）两版。方案完成后系统仍有**两条活跃哈希链记录同一批业务事件**（domain_events 全局链 + order_snapshots 每单森林链）——活跃链数量 2→2，无净减；冻结表只是第三张静态表。窄口径（零消费）确被治愈（新链有中继/R3‘/外锚三个消费方）；宽口径（双链结构冗余）要到 P4 那个被三处（§3/§4 P4/§7）明确解绑为“可分离、不构成本方案前置”的评估项裁决后才可能消除——若 P4 评估决定保留，双链结构永续。§0 用了“结构上”三字，恰恰选中了自己没交付的那一口径。
3. **“消失”不带任何条件限定**。R2 的消失依赖中继事务接入互斥队列（稿中未写，见 P1-L1）；R3 的消失依赖 M5 循环被替换（稿中未写，见 P1-L2）。三个“消失”各自吊在未写明的实现前提上，§0 全称宣称。

**理由**：§0 是审批第一入口的承重陈述。按承重陈述出口定律（无限定的承重宣称）与呈报纪律②（背书须附条件），此句以审批者无法在 §0 处看见的方式夸大了治根范围——“治标（零消费症状）包装成治根（结构消除）”的实锤即在此句。P0。

## P1（6 项）

### P1-L1 R2“自锁从结构消失”缺失使能前提——中继事务的互斥接线与并发面全文未写

**位置**：§3 改造后图中继段（行 53-55）、§1 R2 行（行 21）；对照 C 员约束 C1/C2（db-write-mutex.ts:1-17,26 实读核实）。

**论证**：中继“算 seq/prevHash/recordHash → 同中继事务补链列”是一笔**显式写事务**。按现行架构不变式 C2（进程级全部写事务必须经 runExclusiveWrite 排队）与 C1（sqlite 全库单共享连接，交叉 BEGIN/COMMIT=悬挂事务/幽灵写病——db-write-mutex.ts:2-9 头注原文），中继事务必须入同一互斥队列——稿中通篇未写这一接线。逻辑推演两分支：(a) 若按字面实现不入队：中继事务与业务事务在 sqlite 单连接上交叉 → 复活的不是 R2 死锁，而是 M3 之前的悬挂事务病（更隐蔽）；(b) 若入队：无嵌套=确无新死锁面（此点方案成立），但中继在持锁窗口内做哈希计算+UPDATE，与业务写形成新的串行竞争点，稿中未评估。另两未写面：多实例部署（仓内有 k8s/）下进程级互斥跨不了实例，双中继竞争 seq 的防线（新表是否保留唯一索引类并发后防线）未定义；中继“定时/事件驱动”双触发并发自救未提。

**理由**：“从结构消失”是承重结论，其成立与否恰好取决于这条未写明的接线；评审席无法验证宣称。评审提问“会不会形成新死锁面”的独立答案：死锁面无（无嵌套路径）、竞争面有、乱接线则复活旧病——三者稿中均无交代。P1。

### P1-L2 R3 的 M5 路径去向未写明——替代/并存二义 + 类 2 事件 fail 语义翻转未论证

**位置**：§1 R3 行（行 22）、§3 改造后图（行 47-60，M5 审计循环在图中无声消失）；对照 orders.service.ts:215-244（实读核实：M5 循环锁外、事务外、逐条 await、catch 仅 warn）。

**论证**：现状 create() 三段：①事务（业务+快照）②互斥块外 created 事件 ③M5 审计循环（fail-open 且在请求延迟路径上逐条抢全局互斥）。改造后图只有两段+异步中继——M5 循环被沉默摘除，但稿中无一字说明 PRODUCT_AUTO_UNLIST 事件的归宿：(a) 若改为事务内 outbox 行，则类 2（系统派生事件）语义从 fail-open **翻转为 fail-closed**——审计事件行 INSERT 失败将回滚订单本体；v5 的三分类（user/admin mutation、系统派生、敏感 admin）讨论被整体丢弃且未交代；D 员 Q2 明示四标准均无“审计失败须阻断业务”要求、标准路径=检测+告警+补写，翻转是可用性代价，须论证而未论证。(b) 若保留旧循环，则 P2 冻结 audit_logs 后该循环写向何处？R3“同函数矛盾消失”不成立。商品路径 W6 同题且更严重：商品 create/delete 是单语句 autocommit（C 员 W6 实证），“随业务事务同 INSERT”在该路径无处挂靠（见 P1-L3）。改后 create() 是几段的正确答案是“两段同步+异步中继——**前提**是 M5 被替代”，而这个前提稿中不存在。

**理由**：“同函数矛盾消失”是三大根因宣称之一，其成立恰好吊在未写明的替换关系上。P1。

### P1-L3 存储内带 fail-closed 在单语句 autocommit 写路径上缺少成立前提——P1/P3 退款责任分工矛盾

**位置**：§2 W12 行（行 28：“事件行随退款事务同 INSERT”）、§4 P1（行 78：“订单/商品/退款路径挂 INSERT”）vs P3（行 80：“退款事件补全”）；对照 C 员 W5/W6/W8/W11/W12 实证（payment-application.service.ts:95-208/371-449/526-569、products 路径单语句 autocommit、无显式事务）。

**论证**：W12 退款路径现状**无任何显式事务**可“同 INSERT”——要兑现存储 fail-closed 必须先给该路径引入事务（并按 C2 入互斥队列），这是一项写路径结构改造，迁移路径未列。W5/W6 商品路径同构问题（无显式 BEGIN）。W8/W11 只说“纳入 runExclusiveWrite **或**验证单语句 autocommit 安全性”——双出路无裁决判据；且即便纳入互斥，两个 autocommit 语句（业务+事件行）之间仍非原子：第一条成功第二条失败=事件缺失，“业务成功⇒事件必然存在”在这些路径上不成立。退款责任在 P1（“退款路径挂 INSERT”）与 P3（“退款事件补全”）两处重复列名、无边界说明。

**理由**：存储内带 fail-closed 是方案对 R3 与 W12 覆盖义务的核心承诺，其在退款/商品/支付多条路径上缺少成立前提而迁移路径未揭示，且阶段分工自相矛盾。P1。

### P1-L4 备选落选理由“同事务双写死锁不可修（结构性的）”与本方案自身机制字面矛盾——死锁真因未指明，修补版 v5 未被排除

### P2-L5 §0“每个构件都有文献与业界先例背书”无限定——链化构件的背书是量级条件式，条件在稿内自认“待证”

**位置**：§0（行 12）、§3 裁决 2（行 65：“事件量级（日订单 <万）在 Crosby-Wallach 判定的‘低事件量可行’域内”）、§7（行 105：“基于 dev 库 30 单现状推断，生产量级待证”）；对照 A 员卡2 逐字（"Hash chaining schemes…are only feasible with low event volumes…"）。

**论证**：方案自引的 Crosby-Wallach 把纯哈希链判为仅低事件量可行；方案的链化构件建立在该条件上，而“日订单 <万”是推断数字非实测（稿中 §7 自认），且无复现命令（数字三件套缺件，细节归数字路）。若生产量级越域，链化形态须换 Merkle（§3 裁决 2 已预留）——构件背书条件式，§0 全称宣称与 §7 待证自认不一致。“三个根因消失”本身不随量级坍塌（根因不依赖链形态），坍的是“每个构件都有背书”这句。

**理由**：承重宣称缺少自身已识别的条件限定（任务点 2b 的答案：§0 的“消失”未被量级条件限定，但量级条件实际只打击构件背书句而非根因消失句——根因消失句的限定缺口已在 P0-L1 立案）。P2。

## 总判定

**逻辑路发现 13 项（1 P0 + 6 P1 + 5 P2 + 1 P3）。**
