**P0-B §3.10 触发器三重缺陷（逻辑路 P0-1 + 数据路 F-2 合并）**
- ①与类 2 补链 UPDATE 正面相撞（异步腿补链/翻 INLINE/attempts/死信全是 UPDATE——触发器落地即 P1 验收判据 3 死信演练被自己的触发器 ABORT）
- ②sqlite 语法错（`BEFORE UPDATE OR DELETE` 系 PostgreSQL 语法——数据路 py 真跑复现 `near "OR": syntax error`）
- ③**TiDB 官方不支持触发器**（docs.pingcap.com FAQ 明列）
修复重设计（§3.10 重写）：
```sql
-- sqlite：两个触发器（单事件），UPDATE 触发器带豁免——只禁"已链化行"的变更
CREATE TRIGGER deny_chained_update BEFORE UPDATE ON domain_events
WHEN OLD.seq IS NOT NULL   -- 豁免窗：PENDING 行（seq NULL）的补链/中继元数据 UPDATE 放行
BEGIN SELECT RAISE(ABORT, 'chained rows are immutable'); END;
CREATE TRIGGER deny_delete BEFORE DELETE ON domain_events
BEGIN SELECT RAISE(ABORT, 'domain_events is append-only'); END;
```
- **TiDB 形态：无触发器**——append-only 改由 **DB 权限**承担（应用账号 `GRANT INSERT,SELECT ON domain_events` + 不授 UPDATE/DELETE；迁移/DROP 需管理账号并留痕）——"双方言各一形"重写为"sqlite=触发器形 / TiDB=权限形"
- **payment_refunds 撤下"同款"**（状态机表——六分类全部处置是 UPDATE，触发器即瘫；该表完整性由条件 UPDATE 协议（规格 c）+ 域事件链间接承载）
- order_snapshots：触发器落地**前置扫描**（W4 软删若以 UPDATE 快照行实现则炸——扫描记录入 P3 排产）
- 防护宣称语限定："已链化行阻止改删，未链化 PENDING 行的防护=payloadHash（INSERT 时计算）+ 补链后不变"
- 判据 7 注入工序注记：**在无触发器测试夹具上执行**（模拟攻击者 DROP TRIGGER/权限绕过后的检出腿）
