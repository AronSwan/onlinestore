# REICH 代码质量纲领 v1.4

> 2026-10-04 · 用户令："代码要先进，高效，健壮，完善，反过拟合"
> 五条判据适用于本项目一切代码工作（前端/后端/脚本/文档中的代码示例）。
> 与既有宪法的关系：voice-sheet 管文案、ui-redesign-brief 管视觉、后端工程纪律暂由本纲领第 1/3 条+docs/safety.md 承担（CLAUDE.md 建档后接管本域，建档时本行更新）、本纲领管代码质量总则。与工作区宪法（ZCodeProject/manuals/PRINCIPLES.md）之争按其 §二位阶裁决（用户令＞宪法正文＞本纲领）；同级细目以更具体者为准。

## 五条判据

### 1. 先进——用当前生态的正确做法，不用十年前的野路子
- 正例：ES module 标准、原生 CSS 能力（container queries/`:has()`/OKLCH）、框架惯用法（Nest 的 Guard/Interceptor 管道）
- 反例：eval 拼脚本、字符串拼 HTML 不转义、jQuery 时代的全局函数堆、复制旧 hack 而不问为什么
- 底线：引入任何非惯用法时必须注释理由

### 2. 高效——性能是功能，数字要量化
- 加载：构建产物体积/请求数 vs 改造前要给数字（如 Tailwind CDN 摘除=去掉 100KB+ 运行时编译器）
- 运行：缓存命中/O(n) 习惯（词表匹配用预编译结构不逐条 includes 全文扫）
- 汇报：涉及性能声称必须带实测数字，"感觉快了"不算

### 3. 健壮——失败路径和成功路径一样认真
- 降级真实存在：@supports 包裹、注入失败页面不塌、规则文件读不到 fail-closed 带日志
- 边界：空输入/超长输入/旧数据（无 factCard 的存量商品）都有明确行为，不靠"应该不会发生"
- 错误：错误信息带定位（哪个字段/哪条规则/哪个文件），不抛裸 500

### 4. 完善——验收清单逐项打勾留证，不做"大体过了"
- 每项交付自带证据：测试输出原文/curl 实录/截图路径/复现命令
- 覆盖面：改动影响到的每条路径都验过，包括反路径（401/403/404）
- 台账：挂账项写清"为什么不做+什么时候做"（"有期"三选一与观察行制度见 docs/BACKLOG.md 记账规则），不静默蒸发
- 构建产物视觉验收纪律（M2 双盲审 P1 教训新增，2026-10-05）：凡涉及 CSS/构建管线的视觉交付，验收必须含 build 产物视觉 diff——仓外 dist + vite preview，关键页在代表视口抽查 computed style 并对比 dev；"只验 dev 未验 build 产物"不算验收（CSS 层叠反转只在 build 产物显形）。

### 5. 反过拟合——修因不修果，禁特判压症状
- 禁止为通过对比/截图/测试而 hack：发现视觉漂移就 `!important` 压住、发现测试红就改断言迁就实现——都是过拟合到基线
- 修复必须能回答"为什么这是正确修法"：根因在层叠规则就在 reset 层补齐，根因在数据形状就在源头修正
- 有意的视觉/行为变化要如实标注为改进，不伪装成"零变化"；无意的变化如实报告为回归
- 单例不立法：一次性现象不提炼成普适规则（触发条件？最硬反例？答不上只记观察）
- **整改系统性判据（用户令 2026-10-10"整改或修复必须是系统性的不短视的"）**：任何整改/修复交付前两问——①病根修了吗（治本=闸门/模式/约定补进流程；合法否定答案="单例无立法面"——裁明记观察行，①过关）？②同类面全扫了吗（同类面=同病根+同构形状的全部出现点，辖域全仓；发现义务全域、修改义务限本批动机面，超面=新动机另立批）？两问不过=打回。治标/治本=两动机，按宪法 §二总闸动机分块或拆 commit；治本须同批落地或入账有期（三选一，见 BACKLOG 记账规则），禁以治标冒充整改完结。
- **两问执行位（v1.4）**：代码施工 commit 动机块尾附一行式——①病根=__/单例无立法面；②同类面=谓词"__"命中 N、处置 M、余量入账 K（谓词按病根机制定义，非语法形态）。工具化施工（映射表/规则 id 可引）以模板代答；填不出即非机械，存疑从严。docs/账本 commit 豁免。计数按承重陈述出口定律三件套（本句以两问执行位在效为条件，位废则此句失效）。里程碑档审计席设靶复核真伪。

## 执法方式

- 实施席任务书按本纲领写验收；审计席按本纲领设靶（尤其第 5 条：审计要专找"压症状"式修复）
- 违反第 5 条的修复一律打回重修；违反 1-4 条按严重度记账
- 严重度口径（v1.4）：P0=资损/安全/数据破坏级，立即停线；P1=功能或契约断裂，批内必修或明示死线；P2=记账择期；P3=卫生项。边缘归类争议升级裁决

## 闸门（v1.4）

三道通用闸：`tsc -b` 零错；jest 改动域口径 `--no-cache --runInBand`；eslint 改动文件 `--no-fix` 零 error；涉前端构建加真 vite build。改动域→套件映射由施工总案当批声明，未声明按全量。
专属闸触发表=附件（docs/gates-trigger-table.md，效力源出本节）：行级增改免修订三同步但附件同 commit 留痕（日期+动机+行摘要）；增删闸类、改阶段闸本体、附件载定义或严重度=实质修订走三同步；附件与正文冲突正文赢即改。闸门类治本的落地=流程件正文+命令+账本行三处可指认，仅账面宣称=未落地。

## 双盲审制度（v1.2，用户令 2026-10-04/05）

本节辖本仓里程碑验收；workspace 通用双盲规程（火炼标准/成本纪律）见 ZCodeProject/manuals/double-blind-review-charter.md，冲突时本仓里程碑以本节为准。

里程碑级验收一律双盲审，**每组维度多 agents 下场（每组 ≥2 席）**：

1. **盲抽离**：审计席任务书只含"范围（commit 区间）+维度（纲领五条）"，**不含实施方任何声称**——汇报数字/白名单/"已知差异"一概不给；commit message 中的声称标注为"待验断言，禁止当作锚定事实"。审计席须独立测定后填数字，与断言比对留给协调席。
2. **组×多席独立**：按维度分组（如 X=功能与安全组、Y=质量纲领组），**每组 ≥2 席**同范围同维度并行；全体审计席互不知晓其他任何席位的存在与结论（组内亦然），禁止通信；各自报告独立成文。
3. **协调席双重比对**：①组间交叉——同一发现多组皆中=高置信直接采纳；②**组内一致性**——同组多席皆中=高置信；单席命中（无论组内组间）=协调席复验裁决；对照原始任务书查共漏。组内分歧本身是信号（审计标准漂移或问题边缘），须记录并追因。
4. **实施侧盲**：实施席不知审计席身份与靶点（agent 隔离天然满足，任务书不得预告审计重点）。
5. **禁串谋**：审计任务书不得引用其他审计席的产出或措辞（同组另一席的存在也不得提及）；协调席汇总前不向任何审计席披露比对结果。
6. **席位伤亡处置**：死亡席位原路原样重派（任务书逐字同款+必要事实更新），已交卷的存活席位产出保留有效，不因同组席位伤亡作废。
